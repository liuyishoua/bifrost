# 票务工作台

## 范围与运行

沿用 DouYin_Spider Web 的原生 HTML/CSS/JavaScript、侧边导航和卡片布局，复用现有 Python 票务引擎。无需前端构建或新增生产依赖。

```bash
python -m web --port 8767
```

访问 http://127.0.0.1:8767 。与原 GUI、简易验证页独立；不会导入它们的登录凭证或自动启动订单。

## 业务契约

- 账号管理的是 12306 账号。每账号独立 Session，扫码绑定上游登录身份；同一身份不能重复绑定多个槽位。
- 账号名称、任务配置、事件保存在 `.runtime_web/workbench.sqlite3`。登录 Cookie 按账号独立保存在 `.runtime_web/sessions/*.cookies`（目录权限 0700，文件权限 0600），请求更新后原子保存，重启恢复后使用时校验。二维码、乘车人证件信息仅驻留内存。只有主动退出或删除账号才删除对应 Cookie。业务会话校验未通过时，先用已有凭证尝试恢复登录中心与业务会话；恢复成功并核验原账号身份后继续。网络超时、限流、未知响应保留凭证，只提示稍后重试；登录中心明确返回未登录或失效才要求扫码。账号卡片显示近期会话摘要；完整历史追加保存在 SQLite 的 `session_history` 表，不按20条截断，账号页“会话记录”可分页查看。旧版已有摘要迁移一次，缺失的旧记录无法补回。
- 查询展示上游返回的全部车次和席别，支持类型、车次、实际出发/到达站、时间、席别、有票筛选及排序。预售期内查询实时车票；超过15天时查询近期同星期参考车次，隐藏参考日余票数量并明确标识，目标乘车日期不变。出发站、到达站可点击打开车站列表，支持常用城市按站名筛选、搜索和分页；预约从查询结果中的车次进入。
- 抢票配置明确账号、该账号乘车人、日期/区间、车次优先级、席别优先级、车次优先/席别优先、起止时间、间隔、最大次数、座位/铺位偏好。
- 创建后任务为待启动；明确点击启动才执行。新任务统一自动提交订单，不提供仅提醒模式。
- 同账号同时一个任务，多个账号可并行。创建请求幂等；重复启动不重复执行。开始前验证登录、配置、乘车人；不足人数的数字余票不下单。
- 不把异常当无票。连续查询失败三次停止；登录失效停止。订单链路拒绝停止；提交后结果不确定时停止并标记需核对，避免自动重复下单。
- 成功后展示订单号和官方支付入口。账号保持需核对状态，用户在官方处理完毕后手动解除。此操作仅是用户确认，不冒充上游订单验证。
- 停止是协作式取消。提交后停止不能撤销订单，需到官方核对。普通执行任务重启后标为中断；预约尚未尝试提交时恢复等待，已尝试提交则中断并需核对，绝不自动重试订单。
- 定时任务复用原引擎的服务器校时与单调时钟等待；同步失败会记录回退到本机时间。页面手动时间按北京时间填写。
- 诊断仅记录接口名称、HTTP 状态、上游状态/业务码和脱敏消息；不记录 Cookie、Token 或证件信息。

## 验证

离线测试使用临时数据库和模拟响应检查工作台初始化、席别资料、会话校验、订单重定向保护和预约时间计算，不向 12306 提交订单。真实多账号登录和真实出票需要在工作台中另外验证。

```bash
PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 python -m pytest -q web/tests/test_workbench.py web/tests/test_reservations.py
```

单个任务保留最近150条事件，账号和任务记录保留在本地数据库。请勿上传数据库；其包含账号备注、乘车人姓名和任务信息，但不含登录凭证及证件号。

## 日常使用

1. 账号管理 → 添加账号 → 扫码登录。每个账号使用对应的12306 App身份确认。
2. 查询车票 → 选择空闲在线账号、出发站、到达站、日期。用席别、时段、车次类型等条件筛选。
3. 在车次行点击抢票 → 选择执行账号及成人乘车人 → 配置车次和席别顺序、模式、起止时间、间隔。
4. 保存配置后到抢票任务点击启动。自动提交模式会再次显示完整任务信息，确认后才运行。
5. 任务详情显示状态和脱敏接口返回。订单生成后前往12306支付；需要再次使用账号时，先处理官方订单，再点击账号卡片的已处理官方订单。

当前不实现候补购票、支付、取消官方订单和儿童/学生优惠票。保存后须明确点击启动；启动后发现符合条件的票会自动提交订单。账号会话独立保存在 `.runtime_web/sessions/`，不能与旧的简易测试页共享，避免串号。

## 超预售期预约

选择未来日期 → 查询近期参考车次并点击预约→ 选账号、乘车人和席别 → 保存 → 启动预约。预约是本程序的自动执行安排，不是12306官方已受理的订单。

预约使用 SQLite 保存配置、状态、逐车次核验结果、已用次数及下次检查时间。预计开售日（乘车日期减14天）北京时间00:00、00:20、00:40核验具体车次；错过凌晨才启动则立即查，后续各间隔20分钟。延迟或重启不连续补发，次数不重置。等待期间不占用账号，本机服务必须运行且机器不能休眠。

明确起售公告或已可售状态才算确认，参考车次和车站通用时间均不作为执行依据。每个车次确认后停止核验；未确认车次最多3轮，网络失败也计数。三轮全部未确认则进入“起售时间未确认”，停止任务。部分确认时按最早已确认时间准备抢票；进入抢票后不再单独核验剩余车次，正式查询仍使用全部所选车次的目标日期实时余票。凌晨不保证有公告，特殊预售安排不能仅凭日期公式获知。

准备完成后，从起售前1秒至起售后60秒使用开售间隔（默认0.5秒，可设0.2—300秒）；之后使用常规间隔（默认3秒）。按请求开始时间计算间隔，扣除已用时间，始终串行，不追赶补发。保留最大次数、结束时间、连续三次查询失败停止、订单不确定停止等限制。HTTP Date只有秒级信息，提前查询用于覆盖误差，不代表能精确命中服务端放票时刻。详情记录首轮调度偏差（相对估算服务端时间）、查询耗时和间隔。

重启后恢复各账号 Cookie；已启动且未尝试提交的预约仍保留，执行前校验会话。仅在会话明确失效时需要重新扫码。普通待启动任务仍须点击启动；测试和升级不会替用户启动真实订单。

验证：
```bash
PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 python -m pytest -q web/tests/test_workbench.py web/tests/test_reservations.py
```
实际服务上的调度精度及浏览器操作仍需单独验收。

## 车次列表、逐车席别与规则说明

任务表单支持从列表选择或输入车次，点击“＋ 添加车次”，用上下箭头调整车次优先级。每个车次单独显示参考资料中存在的席别；按勾选顺序决定席别顺序，也可点击席别的上移按钮。未查到参考资料时可刷新车次，不按 G/Z/K 等字母猜席别、不允许保存凭空指定的席别。

参考资料保存在同一 SQLite 数据库的 `train_catalog` 表，主键为出发站、到达站、车次；保存资料日期、席别、发到时刻和采集时间，不保存余票数量或提交凭证。新任务的 `train_options` 绑定每趟车的席别，后端验证并在实际选票时过滤。原有任务仍保留创建时的共用席别偏好。

每个任务的“规则说明”解释当前模式、逐车选择、时间依据、准备/查询窗口、次数与截止限制以及各个状态。页面明确区分：

- 车站规则预计时间：乘车日减14天，加上官方车站通用时间；尚未核验目标车次公告。
- 车次公告时间：目标日期车次实际返回起售公告，保留公告文本及核验时间。
- 目标日期已可售：实际查询已标记可售，只说明可售状态，不反推精确的首次放票时间，更不代表有余票。

例如用户的2026-09-30北京丰台→南昌Z111，预计2026-09-16 08:00来自15天规则及北京丰台站0800记录，不能当作9月30日Z111已确认的起售公告。旧预约缺少来源字段时，升级后重新查询官方时间并补齐证据。

本地“已预约”未向12306占票；提交受理/排队不等于成功；只有流程成功且取得订单号才显示待支付。没有订单号或官方返回未处理订单等情况进入需核对状态，详情保留脱敏业务提示，不会重复提交。

## 填写时即可查看执行安排

表单取消执行模式选择，新任务统一自动提交。默认自动安排开售；查询间隔、最大次数、手动开始和结束时间放入折叠的高级设置。

填写时只读 `sale-plan` 返回凌晨三次核验计划，不查询或猜测具体起售时刻，也不创建任务。保存仍是草稿，点击启动后才执行。

确认起售时间后，提前120秒检查账号和乘车人并校时，提前1秒进入正式余票查询；已可售则立即准备。账号忙或未登录时约15秒检查执行条件，不会重新进行起售公告核验。正式余票查询与凌晨核验分别计数。

如果旧数据存在仅提醒的待启动/预约任务，升级后回到待启动并提示规则变化；不会把此前的提醒授权直接变成后台下单。已明确自动提交的预约保留。

### 会话问题诊断

每次检查登录、扫码、查票、乘车人查询、任务执行、服务恢复和主动退出都有独立 `trace_id`；同一操作的业务校验与自动恢复沿用该编号。`instance_id` 区分服务实例，任务检查额外记录任务ID。

认证接口记录时间、耗时、HTTP状态、重定向状态、业务码、响应格式、失败类型和Cookie数量/过期数量等元信息。区分连接/读取超时、TLS、代理、DNS/连接错误、限流、上游错误、非JSON和字段缺失。凭证读取、更新保存、删除失败及二维码状态另有事件。不会存储请求参数、响应正文、Cookie值、令牌、二维码内容或证件信息。

查询入口：账号页“会话记录”，或只读 `GET /api/accounts/{id}/session-history?before={next_before}`；每页最多50条，新到旧，游标用于继续向前追溯。页面轮询仍只携带近期摘要。数据库写入失败时账号页明确显示诊断异常，不默认为日志完整。

日志可还原本程序何时、在哪一步失败及如何处理；若12306仅返回“未登录”，不能据此推断平台内部是到期、其他终端登录还是风控。未知原因保留未知。测试使用模拟故障与本地HTTP，不提交真实订单。

### 创建任务的交互

新任务自动安排开售核验及开始查询，表单不再提供手动开始、结束时间或切换手动模式。常规余票查询默认60秒；开售窗口仍默认0.5秒。保存时未传常规间隔，服务端同样补为60秒。已有任务按原配置执行，不批量修改历史定时或间隔。

选座显示相对位置示意图，标注靠窗/中间/过道；多种席别只显示共同可用的位置。商务座车型尚未确定时使用A/F交集。单人只显示同一排，多人可选择相邻排；选择数量必须等于乘车人数，或清空使用系统分配。选铺按每位乘车人选择上/中/下铺，混选不支持中铺的席别时不显示中铺。人数或席别变化使原偏好不适用时，重置并提示。偏好不保证满足，运行时继续按原引擎能力判断，不支持时由系统分配。

预约添加备选车次默认合并同城已收录参考资料，城市归属使用 `assets/station_cities.json` 中的12306站点映射，不按站名包含关系推断。列表和已选卡片显示实际起终站，可勾选“仅看相同出发站、到达站”。同一车次只选择一次，有多个停靠组合时优先原查询车站；未收录车次需先查询对应区间以补充参考资料。查询页的原有查询范围不变。

每个备选保存实际车站，执行按已选站点组合分别查询，候选筛选再次校验车次、实际车站、席别。旧任务缺少逐车次车站字段时继续使用原任务车站，不自动扩展旧预约。多区间请求串行执行，一轮可能包含多次请求，查询间隔不代表每个区间都能在该时间内返回。

站点弹窗搜索框支持回车：优先选择完整同名站，否则仅在唯一匹配时直接选中；多匹配保留列表，中文输入法组合期间不触发选择。
